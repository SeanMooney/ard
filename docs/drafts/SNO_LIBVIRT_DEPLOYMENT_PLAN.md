# SNO on libvirt: collaborative design draft

## Status

This is an **unapproved working design** derived from the review of
`ard-libvirt-sno-development-guide.md` and subsequent design discussion. It is
not an implementation plan approved in full.

The source guide remains unchanged. This document records:

- findings confirmed against the current ARD implementation;
- decisions agreed during review;
- proposed implementation boundaries; and
- questions that remain open.

No implementation, deployment, or migration is authorized by this document.

## Desired outcome

ARD should support:

```text
libvirt -> standalone SNO
```

and:

```text
libvirt -> SNO -> upstream OKO control plane -> one EDPM compute
```

The same design must work with local libvirt or a remote libvirt execution host.
Development will use the remote host first.

SNO remains a workload, not a provider. Libvirt continues to own VM, disk,
network, boot-media attachment, start/stop, and destroy operations through
execution-host-local `qemu:///system`.

The initial target is an upstream development environment. This design does
not claim that SNO is a supported production RHOSO control-plane topology.

### Longer-term motivation, not current scope

The eventual environment may use SNO as the ACM/HyperShift management cluster
and the deployed OpenStack cloud to host three OpenShift VMs. On the current
single physical host this would mean nested virtualization through the EDPM VM.
The exact guest roles, HostedCluster layout, sizing, and networking are not yet
known and are outside this plan.

The immediate sequence remains:

1. standalone SNO;
2. SNO-backed OKO with one large EDPM VM;
3. reproduction on the better-resourced target system; and only then
4. design and validation of the eventual three-VM OpenShift workload.

The current EDPM shape preserves nested-cloud capacity where practical, but
booting three OpenShift Nova guests is not an acceptance criterion for the
initial SNO or SNO-backed OKO work. A future phase must measure nested KVM CPU
features, memory pressure, image/volume growth, MTU, and guest networking before
claiming that topology is viable. A dedicated bare-metal EDPM node remains a
possible fallback if the extra virtualization layer is impractical.

## Agreed decisions

### Workload and topology model

- Standalone SNO uses `ard_workload: sno`.
- SNO is parallel to the existing `microshift` workload.
- SNO-backed OKO uses a distinct OKO topology with one SNO control-plane VM and
  one EDPM compute VM.
- Working topology names are:
  - `sno/single-node`;
  - `oko/sno-one-edpm-compute`.
- A topology may derive and persist an internal substrate value, but users
  should not have to set a second selector that can conflict with the topology.

### Remote execution boundary

- `openshift-install` and automated `oc` commands run on the remote libvirt
  execution host because the Ansible controller is not expected to reach guest
  networks directly.
- Allowing installer and cluster-client tooling on the execution host does not
  permit DevStack, EDPM, NFS package configuration, or other guest workload
  preparation to target the hypervisor.
- No controller-to-API tunnel or proxy feature is required.
- Each deployment has its own remote installer directory, `oc` binary reference,
  and kubeconfig so multiple SNO deployments can coexist.
- Cluster FQDNs must be unique on an execution host. A literal shared
  `sno.ard.test` identity cannot be reused concurrently by multiple deployments.

### Installer inputs and state

- ARD renders protected `install-config.yaml` and `agent-config.yaml` inputs
  locally under the deployment directory.
- ARD synchronizes those inputs to the execution host.
- `openshift-install` runs on the execution host.
- State generated by `openshift-install` remains authoritative on the execution
  host.
- Protected copies of kubeconfig and selected artifacts may be archived in the
  local deployment directory, but local copies are not expected to provide
  direct API connectivity.
- Non-secret provider state records remote paths, versions, phases, and owned
  resources. It never contains pull-secret, kubeconfig, token, or password
  content.

### Installer and client binaries

- ARD resolves the selected exact OpenShift release.
- The execution host downloads and validates matching `openshift-install` and
  `oc` binaries for its architecture.
- A per-deployment remote cache is keyed by exact release and architecture.
- Tools and their verified archives remain inside the deployment's remote
  directory so deleting that directory removes all deployment-owned files.
- One deployment must not silently change another deployment's tools.
- The initial release policy is to resolve the latest stable OpenShift 4.20.z,
  then pin that exact patch for the deployment.

### Generic VM lifecycle

- The SNO VM uses generic provider capabilities rather than SNO-specific
  `virsh` logic:
  - blank root disk;
  - external installation media;
  - configurable start phase.
- A generic per-node setting such as `start_phase: apply | deploy | manual`
  must be usable by any provider VM.
- The SNO VM uses `start_phase: deploy`.
- `apply` prepares installer media, creates networks/disks/domain, attaches the
  ISO, and leaves the SNO VM powered off.
- `deploy` starts the SNO VM and owns OpenShift installation completion.
- This avoids creating a running placeholder VM and later replacing its boot
  mechanism.

### Apply, ping, and default lifecycle

- `apply` gates readiness only for nodes whose `start_phase` is `apply`.
- A powered-off `deploy`-phase SNO domain is a successful apply result.
- `make ping` is an optional diagnostic target, not a lifecycle phase or the
  readiness mechanism for apply.
- Remove `ping` from `make default`.
- Apply and deploy keep their own appropriate readiness gates.

### Inventory behavior

- The RHCOS SNO VM remains a logical Ansible inventory host.
- It uses `core` SSH details for diagnostics.
- It belongs to `sno`, cluster, and an explicit externally-managed group.
- It is excluded from mutable-host groups targeted by Python, cloud-init,
  base-package, and host-network roles.
- Existing mutable roles should target an explicit mutable-host group rather
  than accumulating SNO-specific conditions.

### DNS

- Development uses a deployment-local provider-managed test zone such as
  `ard.test`.
- Libvirt dnsmasq serves the API, API-internal, node, and wildcard applications
  records for each SNO deployment.
- ARD adds an exact route-only resolver rule on the execution host for the
  deployment domain and libvirt bridge.
- Multiple deployments can coexist because resolver routing is domain- and
  bridge-scoped.
- Cleanup removes only resolver state recorded for that deployment.

### Networking ownership

- Provider render allocates management and OKO network identities, ranges,
  VLANs, interface MACs, and MTUs before installation.
- Standalone SNO AgentConfig contains its management network configuration.
- SNO-backed OKO AgentConfig contains the complete second-NIC, `ospbr`,
  ctlplane-address, MTU, and VLAN configuration from first boot.
- Deploy validates host networking rather than reconfiguring it after SNO is
  installed.
- Kubernetes objects such as NetworkAttachmentDefinitions and MetalLB resources
  remain part of OKO deploy.
- Existing KubeVirt GRETAP/veth behavior and direct-libvirt EDPM `nic2`/`eth1`
  behavior must remain unchanged.

### Resource ceiling and initial shapes

The complete SNO-backed OKO environment must stay within:

- 32 allocated vCPUs;
- 80 GiB allocated guest RAM; and
- 250–300 GB total virtual disk capacity.

This leaves dev-host capacity for the host OS, image cache, Agent ISO and state,
logs, and qcow2 growth. Thin provisioning does not waive the allocation limit.

Initial shapes:

| VM | vCPU | RAM | Root disk |
| --- | ---: | ---: | ---: |
| Standalone SNO | 8 | 16 GiB | 120 GB |
| OKO SNO | 12 | 20 GiB | 150 GB |
| OKO EDPM | 16 | 60 GiB | 120 GB |

The OKO topology totals 28 vCPU, 80 GiB RAM, and 270 GB of virtual disks.
Host pressure must be measured during validation. The large EDPM allocation is
intended to leave room for later nested Nova guests, but their count and roles
remain outside the initial acceptance criteria.

### Kubernetes PVC storage

- Standalone SNO phase one installs the same local-path provisioner used by the
  MicroShift path.
- Mark `local-path` as the default StorageClass and validate it with a PVC write
  test before standalone deploy is complete.
- The initial SNO-backed OKO environment does not add a dedicated SNO data disk.
- Local-path consumes capacity from the SNO root filesystem and remains the
  selected OKO StorageClass initially.
- This is explicitly development-only storage, not a production OpenShift
  storage recommendation.

### Cinder NFS placement

- The preferred self-contained design hosts the Cinder NFS service on SNO.
- NFS must not run on the EDPM node.
- NFS on the execution host is an acceptable development fallback, but not the
  preferred topology.
- The intended self-contained shape is an in-cluster NFS server or Ganesha
  workload backed by a local-path PVC on SNO.
- The exact server implementation, privilege/SCC requirements, effective quota,
  stable endpoint, and EDPM mount path remain unresolved and require focused
  review before implementation.

### Media finalization

After the installer reports success, deploy must:

1. detach the Agent ISO from live and persistent domain configuration;
2. reboot SNO from the installed root disk;
3. revalidate API access, ClusterVersion, and node readiness; and
4. record that media detachment and disk-boot validation completed.

A completed repeated deploy must not detach or reboot again unnecessarily.

### Retry and cleanup

- A failed or interrupted deploy may resume installer wait and validation only
  when recorded inputs, ISO, disk, and domain still match.
- Retry never regenerates the ISO, replaces disks, or restarts installation
  automatically.
- Input drift or irrecoverable installer failure stops with diagnostics.
- Normal destroy removes provider resources but preserves protected local inputs,
  remote installer state, kubeconfig, and diagnostics.
- Recreating the same deployment after normal destroy is refused.
- Users must run `destroy-clean-generated` before a fresh apply of that deployment.
- `destroy-clean-generated` removes protected local and remote installer state
  only after exact provider cleanup succeeds.
- Automatic installer generations and tombstones are not part of this design.

## Review of the baseline proposal

### Direction that remains valid

The baseline correctly separates:

```text
provider infrastructure
cluster installation
OpenStack workload deployment
```

It also correctly chooses the Agent-based Installer as the initial mechanism
and identifies provider-rendered IP/MAC identity as input to AgentConfig.

ARD already allocates deterministic IPs and MACs before VM creation in:

`ansible/roles/ard_provider_render/templates/nodes.yaml.j2`

A provisional VM is not required to discover final identity.

### Current ARD assumptions that must change

1. **Libvirt currently assumes cloud images.**
   `ansible/roles/ard_libvirt_node/` clones a base qcow2, creates cloud-init
   media, and boots from disk. It needs generic blank-disk and installation-media
   support while preserving the existing cloud-image path.
2. **Apply assumes all nodes become mutable SSH hosts.**
   `ansible/playbooks/provider/apply.yaml` waits for SSH/cloud-init and installs
   packages on all provider nodes. Those roles must target only mutable nodes.
3. **Inventory always assumes `stack` and Python.**
   `ansible/roles/ard_libvirt_inventory/tasks/main.yml` needs per-node access
   identity and externally-managed classification.
4. **Libvirt DNS has no wildcard input.**
   `ansible/roles/ard_libvirt_network/templates/network.xml.j2` currently emits
   DHCP reservations only.
5. **OKO is coupled to the MicroShift host.**
   `ansible/playbooks/workloads/oko/converge.yaml` installs MicroShift
   unconditionally. `deploy_oko` mixes Kubernetes API operations with mutable
   host networking and NFS package configuration.
6. **There is no remote cluster-client runner abstraction.**
   For SNO, locally rendered OKO manifests must be synchronized to the
   per-deployment execution-host directory and applied there with its `oc` and
   kubeconfig.
7. **Provider-state writers replace whole documents.**
   SNO introduces additional lifecycle metadata, so state updates must preserve
   provider and workload sections atomically.

### Upstream corrections to retain

- OpenShift 4.20 documents an SNO floor of 8 vCPU, 16 GB RAM, and 120 GB
  storage, and warns that additional Operators increase requirements.
- `controlPlane.replicas` is one, `compute.replicas` is zero, platform is none,
  and OVN-Kubernetes is required for SNO.
- AgentConfig cluster name, rendezvous IP, machine network, node IP, MAC,
  gateway, and DNS must form one coherent configuration.
- If multiple disks are later added, root-device selection must be explicit.
- `.local` should not be used for the managed development DNS suffix.
- The Agent ISO is not a complete disconnected payload; target nodes still need
  release-image registry or mirror access.
- The exact Agent-media freshness rule must be verified for the selected 4.20.z
  release. The reviewed 24-hour warning applies explicitly to a manual
  coreos-installer flow and must not be assumed identical without evidence.
- Host binary architecture and target payload architecture are distinct values.
- SNO-backed upstream OKO is a development target, not automatically a supported
  RHOSO product topology.

## Proposed render contract

Standalone example:

```yaml
---
ard_render_schema_version: 1
ard_provider: libvirt
ard_provider_profile: local-libvirt
ard_workload: sno
ard_workload_topology: single-node
ard_service_profiles: []
ard_openshift_version: 4.20.<pinned-patch>
ard_openshift_cluster_name: <deployment-unique-name>
ard_openshift_base_domain: ard.test
```

OKO example:

```yaml
---
ard_render_schema_version: 1
ard_provider: libvirt
ard_provider_profile: local-libvirt
ard_workload: oko
ard_workload_topology: sno-one-edpm-compute
ard_service_profiles: []
ard_openshift_version: 4.20.<pinned-patch>
ard_openshift_cluster_name: <deployment-unique-name>
ard_openshift_base_domain: ard.test
```

Render derives provider machine CIDR, gateway, DNS, node IP, and MAC. Those
values are not independently repeated in OpenShift input.

Secret and site-local inputs belong in deployment-local variables:

```yaml
ard_openshift_pull_secret_file: /secure/path/pull-secret
ard_openshift_ssh_public_key_file: ~/.ssh/id_ed25519_stack.pub
ard_libvirt_execution_host:
  name: virt-host
```

Execution-host work defaults to the unprivileged Ansible user. ARD-owned
runtime images, rendered XML, caches, temporary files, tools, and protected
installer state live under one `~/ard/<deployment>/` directory. Individual
tasks may elevate only when a demonstrated host operation requires it, such as
resolver configuration or SELinux labeling. Libvirt and systemd-resolved keep
their daemon-managed definitions and runtime state in system locations, so the
supported destroy flow must remove recorded resources before the deployment
directory itself is deleted.

Proxy, mirror, additional-trust, and NTP inputs should reuse existing ARD
settings where possible. The first implementation must either support a
non-empty value or reject it explicitly; it must not ignore it.

## Proposed generic provider contract

Illustrative rendered node data:

```yaml
provisioning:
  method: install-media
  root_disk:
    source: blank
    size_gb: 120
  install_media:
    remote_path: <deployment-runtime>/sno/agent.iso
lifecycle:
  start_phase: deploy
management:
  mode: externally-managed
  ansible_user: core
```

Existing nodes retain:

```yaml
provisioning:
  method: cloud-image
lifecycle:
  start_phase: apply
management:
  mode: mutable
  ansible_user: stack
```

Names are illustrative and still open to refinement. The behavior, rather than
these exact keys, is agreed.

Provider responsibilities:

- atomically create the blank root disk;
- own the remote ISO attachment path;
- define a powered-off domain for `start_phase: deploy`;
- start domains only in the configured phase;
- detach media when requested by deploy;
- own reboot and domain-state checks;
- record exact disk/media/domain/network/DNS ownership; and
- remove only recorded owned resources.

SNO workload responsibilities:

- render protected inputs locally;
- synchronize inputs to the execution host;
- resolve/download/cache matching tools;
- generate and validate Agent media before provider definition;
- start installation through the generic deploy-phase start action;
- run installer wait and `oc` checks on the execution host;
- synchronize OKO manifests to the remote deployment directory;
- request generic media detach/reboot after successful install; and
- preserve or clean installer state according to lifecycle policy.

## Proposed directories and state

Controller-local protected data:

```text
deployments/<name>/
  sno/
    inputs/                    # mode 0700
      install-config.yaml      # mode 0600, secret-bearing
      agent-config.yaml        # mode 0600
    auth/                      # protected archive copy when fetched
      kubeconfig
      kubeadmin-password
    redacted-install-config.yaml
```

Execution-host deployment layout:

```text
~/ard/<deployment>/
  cache/
    agent/
    openshift/<exact-version>/<architecture>/
      openshift-install
      oc
  tmp/
  images/
  rendered/libvirt/
  bin/
  sno/
    bin/
    installer/
    auth/
    manifests/oko/
```

The protected state root must be outside the deployment's disposable `images/`
and `rendered/` subtrees.
The installer directory is stateful and authoritative remotely and survives
normal provider destroy. It is not silently reused for another installation.
The generated ISO is copied into the provider-owned libvirt runtime tree for
QEMU; normal destroy removes that runtime copy while preserving the protected
installer directory. Exact path defaults and integration with existing
recursive libvirt runtime cleanup remain implementation details to resolve.

Non-secret local `provider-state.yaml` should record at least:

```yaml
ard_cluster_substrate: sno
sno:
  requested_version: 4.20.<patch>
  installer_version: <exact-output>
  release_image: <resolved-reference-or-digest>
  remote_install_dir: <path>
  remote_iso: <path>
  remote_oc: <path>
  remote_kubeconfig: <path>
  phase: prepared | resources_created | installing | complete | media_detached | disk_boot_validated
```

The existing libvirt execution and inventory state writers must use one
merge-preserving atomic state-update boundary so neither provider nor SNO state
is lost.

## Proposed lifecycle semantics

### `make render`

- Resolve SNO or SNO-backed OKO topology.
- Allocate final provider identities, networks, IPs, and MACs.
- Persist non-secret intent.
- Do not read the pull secret, contact the execution host, download tools, or
  generate media.

### `make apply`

Internal SNO preparation before provider creation:

1. validate local secret/public-key inputs;
2. render protected installer inputs locally;
3. synchronize them to the per-deployment remote directory;
4. resolve/download/cache exact installer and client binaries;
5. run `agent create image` remotely; and
6. record and validate the resulting remote ISO.

Provider apply then:

1. creates libvirt network and DNS records;
2. installs the execution-host resolver route;
3. creates blank root disk and domain with Agent ISO attached;
4. leaves the SNO domain powered off;
5. creates and starts normal apply-phase nodes, including EDPM;
6. waits for readiness only on mutable apply-phase nodes; and
7. writes logical inventory including externally-managed SNO.

### `make ping`

This remains an explicit diagnostic. It is removed from `make default` and does
not gate SNO lifecycle state.

### `make deploy`

Standalone SNO deploy:

1. verify provider/input/media identity;
2. start the SNO domain through the generic provider action;
3. run or resume `openshift-install agent wait-for install-complete` remotely;
4. validate the API and single Ready schedulable node with remote `oc`;
5. install and validate the default local-path StorageClass with a PVC write
   test;
6. detach ISO through the provider;
7. reboot from disk; and
8. revalidate cluster health.

SNO-backed OKO then:

1. validate AgentConfig-created host bridge/VLAN topology;
2. render OKO manifests locally;
3. synchronize them to the remote per-deployment manifest directory;
4. apply/query them using remote per-deployment `oc` and kubeconfig;
5. deploy the chosen in-cluster NFS server when its design is resolved;
6. converge OpenStack control-plane resources;
7. prepare the one EDPM host through its mutable inventory group;
8. converge dataplane resources; and
9. wait for control-plane and dataplane readiness.

Repeated deploy resumes matching incomplete installer state. It does not rebuild
media or disks automatically. Completed phases are idempotently skipped.

### `make verify`

Verify:

- provider ownership and domain state;
- DNS records and execution-host resolver route;
- exact OpenShift version;
- node/API readiness;
- AgentConfig-created bridge/VLAN state;
- local-path PVC smoke test;
- ISO detachment and disk boot;
- remote per-deployment client/kubeconfig paths; and
- OKO/EDPM readiness when selected.

### `make destroy`

- Fail closed using recorded local provider state.
- Remove recorded domains, disks, ISO attachment/runtime media, networks, and
  resolver routing.
- Preserve local protected inputs and remote installer state by default.
- Mark the deployment as requiring clean before reuse.

### `make destroy-clean-generated`

- Complete exact provider cleanup first.
- Then remove protected local SNO artifacts and recorded remote installer state.
- Permit a later fresh apply of the same deployment name.

## DNS design

For an illustrative unique cluster `sno-dev1`, base domain `ard.test`, and node
IP `192.168.119.2`, provider DNS must serve at least:

```text
api.sno-dev1.ard.test         A 192.168.119.2
api-int.sno-dev1.ard.test     A 192.168.119.2
<node-fqdn>                   A 192.168.119.2
*.apps.sno-dev1.ard.test      A 192.168.119.2
```

Use libvirt network DNS/dnsmasq configuration, not `/etc/hosts`, for wildcard
records. Add reverse records if required by the pinned OpenShift release.

The execution host needs a scoped resolver route for the unique cluster domain
through the correct libvirt bridge/gateway. Resolver implementation must
support multiple simultaneous deployment domains, reject FQDN collisions, and
perform exact cleanup.

## OKO platform differences from MicroShift

The SNO path must not mechanically run MicroShift host tasks on RHCOS.

Full OpenShift normally provides or supports:

- OLM;
- Routes and a cluster apps domain;
- Multus;
- OpenShift DNS; and
- operator-managed network/load-balancer integrations.

The SNO path must detect required capabilities and install only missing,
explicit prerequisites. MicroShift-specific CoreDNS, `/etc/hosts`, MetalLB
status, and RabbitMQ workarounds must be capability-gated rather than copied
unconditionally.

The existing OKO role currently mixes:

- Kubernetes API operations;
- mutable MicroShift host networking;
- local manifest synchronization;
- NFS package configuration; and
- EDPM preparation.

Refactor these into substrate-specific preparation plus common manifest/API
operations. MicroShift retains its existing host-local runner. SNO uses the
execution host as its cluster-client runner. This is a small task boundary, not
a generic plugin framework.

## NFS design question

Agreed constraints:

- preferred NFS placement is on SNO;
- it is backed by local-path/root capacity;
- it must be reachable by Cinder pods and the EDPM VM;
- it must not be installed on EDPM;
- execution-host NFS is an acceptable fallback only;
- total virtual disk allocation remains 270 GB.

Still to evaluate:

1. An actual NFS server or NFS-Ganesha controller/deployment. Many components
   called "NFS provisioners" require an existing server and do not create one.
2. Required SCC, privileges, host networking, and kernel capabilities.
3. Whether a local-path PVC provides adequate persistence and capacity behavior.
4. How to bound usage when local-path requested size does not enforce a
   filesystem quota.
5. A stable ctlplane/datacenter endpoint that survives pod restart.
6. EDPM routing, firewall, mount version, and Cinder compatibility.
7. Whether the execution-host fallback should be implemented in the first
   iteration or only documented for recovery.

No NFS implementation is selected yet.

## Implementation sequence proposed for later approval

### Phase 0: Contract-only refactor

- Add generic provisioning method, start phase, and management mode to rendered
  nodes.
- Add mutable and externally-managed inventory groups.
- Make current cloud-image nodes resolve to existing behavior.
- Remove optional `ping` from `make default`.
- Add merge-preserving state update helper.

### Phase 1: Generic libvirt install media

- Add atomic blank-disk creation.
- Add external ISO attachment for powered-off domains.
- Add deploy-phase start, media detach, reboot, and state checks.
- Extend exact destroy ownership.
- Test local and remote delegation without OpenShift.

### Phase 2: SNO render and preparation

- Add `sno/single-node` topology and flavor.
- Add OKO SNO plus one-EDPM topology and flavors.
- Render protected installer inputs locally.
- Add remote versioned tool cache and per-deployment directories.
- Generate Agent media remotely without starting the VM.
- Add provider DNS and scoped execution-host resolver routing.

### Phase 3: Standalone SNO deploy

- Start SNO during deploy.
- Wait/resume installer state remotely.
- Validate with per-deployment remote `oc`.
- Install and smoke-test local-path.
- Detach media, reboot, and revalidate.
- Implement preserve-versus-clean behavior.

### Phase 4: OKO task separation

- Separate MicroShift host preparation from common OKO API operations.
- Add substrate-derived cluster-client runner.
- Keep existing MicroShift and KubeVirt behavior unchanged.

### Phase 5: Self-contained NFS spike

- Compare concrete in-cluster NFS server/Ganesha implementations.
- Validate local-path backing, privileges, endpoint stability, and EDPM access.
- Decide whether execution-host fallback is required.

### Phase 6: SNO-backed OKO

- Validate AgentConfig-created host networking.
- Install required OpenShift-native prerequisites.
- Deploy the selected NFS service.
- Converge control plane and one large EDPM node.
- Measure resource pressure against hard host ceilings.

### Phase 7: End-to-end and documentation

Validate a clean remote lifecycle using a separate deployment and network:

```text
destroy-clean-generated
render
apply
# optional ping only when useful
deploy
verify
destroy
```

Do not disturb the currently running `remote-libvirt-oko` deployment during
this work.

## Test and acceptance outline

### Render and fixture tests

- SNO uses one control-plane replica, zero workers, platform none, and
  OVN-Kubernetes.
- Provider IP/MAC/network values propagate into AgentConfig.
- Standalone and OKO SNO resource ceilings are enforced.
- SNO OKO renders one EDPM node.
- AgentConfig owns complete initial host networking for the OKO topology.
- Pull-secret and credential content never appears in normal output or
  non-secret state.
- Existing cloud-image, MicroShift, static, and KubeVirt renders remain
  unchanged.

### Generic libvirt tests

- Blank disks are atomic and cannot be confused with cloud-image overlays.
- Install media paths are exact, delegated, and recorded.
- Deploy-phase domains remain powered off after apply.
- Generic start/detach/reboot operations are idempotent.
- Partial apply leaves enough state for exact cleanup.
- Destroy removes only recorded owned resources.
- Existing apply-phase nodes retain SSH/cloud-init readiness behavior.

### Standalone SNO acceptance

- Render, apply, deploy, verify, and destroy work on remote libvirt.
- Exact 4.20.z installer/client versions are cached and selected.
- Execution-host DNS resolves deployment API and apps records.
- SNO installs from a powered-off apply result.
- Resume deploy continues matching installer state.
- Node becomes Ready and schedulable.
- `local-path` is the default StorageClass and its PVC write test succeeds.
- ISO detaches and disk reboot revalidates successfully.
- Normal destroy preserves installer state and blocks recreation.
- Clean destroy permits a fresh deployment.

### SNO-backed OKO acceptance

- Total topology remains at or below 32 vCPU, 80 GiB RAM, and 300 GB disks.
- SNO host networking is correct from first boot and is not reconfigured later.
- OKO API operations run with deployment-specific remote `oc` and kubeconfig.
- Local-path provides control-plane PVCs.
- Selected SNO-hosted NFS service is reachable from Cinder and EDPM.
- OpenStack control plane and the one EDPM deployment become Ready.
- Existing MicroShift OKO and KubeVirt OKO behavior remains unchanged.

2. How should local-path-backed NFS capacity be bounded and monitored?

   prepared-but-never-booted deployment be handled?
5. Which exact names should be used for generic provisioning/start/management
   fields and inventory groups?
6. Which OKO/operator-index revision should be pinned with OpenShift 4.20.z?
7. Which full-OpenShift prerequisite Operators must ARD install versus merely
   validate?
